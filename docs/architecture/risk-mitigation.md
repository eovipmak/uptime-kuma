# Risk Register & Mitigation Plan

> Program-level risk register for the multi-tenant Uptime Kuma initiative. Sources: the [multi-tenant plan](../plans/multi_tenant_uptime_kuma_plan.md), the four G0 ADRs, and risks identified during architecture synthesis (task G0.03). Consumed by phase G9 (security/hardening) and referenced by every phase's test planning.
>
> Severity scale: **H** = can cause cross-tenant data exposure, data loss, or program failure; **M** = degraded service or schedule slip; **L** = operational annoyance with a workaround.

## Register

| ID | Risk | Source | Severity | Mitigation | Owning Phase |
| --- | --- | --- | --- | --- | --- |
| R1 | **Cross-tenant data leak** via a missed `tenant_id` filter (IDOR class): one query path bypassing the wrapper exposes another tenant's monitors, heartbeats, or status pages | Plan Golden Image principles; [ADR-0002 Consequences](../adr/ADR-0002-isolation-model.md) | H | Triple-layer enforcement: HTTP/socket tenant guards (G2), role gates (G3), tenant-safe repository wrapper injecting `tenant_id` on every query (G4); ESLint rule `require-tenant-scope` catches new unscoped `R.find/R.findOne/R.exec` calls; dedicated IDOR test suite runs from G4 onward and every later phase extends it | G1, G4 |
| R2 | **Noisy neighbor**: one tenant running thousands of monitors delays other tenants' checks or saturates DB writes (single shared schema) | Plan G5 DoD ("no tenant delayed > 10%"); [ADR-0002](../adr/ADR-0002-isolation-model.md) Shared-schema noise | H | Per-tenant staggered scheduler batches with configurable concurrency (`monitorListByTenant`, G5); quota gates at `startMonitor` — max monitors + min check interval (hardcoded until G8 makes them plan-driven); per-tenant heartbeat retention bounds table growth; MariaDB row-level MVCC avoids SQLite single-writer serialization ([ADR-0001](../adr/ADR-0001-database-choice.md)) | G5 |
| R3 | **Migration data loss on rollback**: a failed `exports.down` or botched backfill destroys existing monitoring history during upgrade | Plan G1 DoD ("Rollback does not lose existing data") | H | Contract mandates additive-only up-migrations and down-migrations that only drop what that migration added ([migration contract §Rollback](./migration-contract.md)); backfill is idempotent and re-runnable; migration tests run on empty DB *and* populated-DB copies in CI (G1 task-08); operators advised to snapshot before upgrade (G12 docs) | G1 |
| R4 | **SSRF via monitor URLs**: tenants probe internal services (`http://169.254.169.254/`, localhost, RFC1918) from the server's network position using http/tcp/docker monitor types | Plan security section; synthesis of survey [monitoring-engine.md](./survey/monitoring-engine.md) (server-side fetch in every beat) | H | URL/host validation at monitor create/edit: deny link-local, loopback, and private ranges unless instance-configured allowlist; DNS-rebinding guard (resolve then pin IP); proxy egress policy for docker/snmp types; documented per-deployment policy knobs. Full hardening lands with security phase | G9 |
| R5 | **JWT tampering / tenant claim forgery**: attacker crafts or replays a token claiming another `tid` to land in another tenant's context | [ADR-0003 header trust](../adr/ADR-0003-routing-and-tenant-resolution.md); [ADR-0004](../adr/ADR-0004-authentication-strategy.md) | H | Tokens signed server-side (instance secret, httpOnly SameSite=Lax cookie); `tid` claim is a hint only — `resolveTenant()` re-validates live membership on every use; refresh-token rotation with reuse-detection kills stolen families; removal-while-online revocation hook (G2); RBAC matrix tests include forged/tampered claim cases (G3 task-16) | G2, G9 |
| R6 | **Custom-domain SSL automation failure**: Caddy on-demand TLS fails (rate limits, CNAME not yet propagated, LE outages) leaving tenant status pages unreachable or untrusted | [ADR-0003 Consequences](../adr/ADR-0003-routing-and-tenant-resolution.md); plan G6 | M | CNAME verification flow before domain activation (`status_page_cname` unique constraint as registration anchor); actionable error surfacing to tenant admin; LE **staging** endpoint for dev/staging to avoid quota burn; Nginx+certbot generator as fallback path; on-demand TLS permission module prevents certificate-harvesting abuse | G6, G10 |
| R7 | **Backward-compatibility break** for existing single-user deployments (upgrade bricks installs or changes behavior/results) | Plan mandate "Backward Compatible"; all P0 phases depend on it | H | Default-tenant backfill assigns every legacy row to one default tenant (G1 task-06); legacy admin becomes `tenant_admin` of default tenant with identical UX ([ADR-0004](../adr/ADR-0004-authentication-strategy.md)); SQLite remains fully supported as single-tenant engine ([ADR-0001](../adr/ADR-0001-database-choice.md)); compat assertions required in every phase's test suite (G1–G6 each carry a backward-compat DoD line) | G1 (foundation), all phases G2–G6 (regression duty) |
| R8 | **redbean-node engine ceiling**: ORM supports only MySQL/MariaDB + SQLite (no PostgreSQL driver exists in its dist) — any design assuming Postgres silently fails | Synthesis finding during [ADR-0001](../adr/ADR-0001-database-choice.md) correction; verified against `node_modules/redbean-node` (dialect dir contains only `better-sqlite3`; package engines: mysql, sqlite) | M | Resolved by ADR-0001 revision: target engine is MariaDB via bundled `mysql2`; G1 keeps dual-dialect (SQLite + MariaDB) migration branches per repo convention; no third dialect introduced without a new ADR | G1 |
| R9 | **Index parity gap on hot path**: SQLite-only partial indexes (`WHERE important = 1`) on `heartbeat` cannot port to MariaDB; multi-tenant beat volume hits full composite indexes instead | Survey [database-schema.md §heartbeat](./survey/database-schema.md#heartbeat); [ADR-0001 Consequences](../adr/ADR-0001-database-choice.md) | M | Accept pre-existing upstream MariaDB behavior (regular composites) rather than degrade further; benchmark `monitor_important_time_index` shape under synthetic multi-tenant load in G5 staging (≥100 tenants × 50 monitors DoD); revisit only if p95 beat-write latency regresses vs SQLite baseline | G5 |
| R10 | **Tenant deletion cascade latency/locks**: deleting a tenant cascades FK deletes across ~15 tables including write-hot children; long transactions block beats and retention jobs | [ADR-0002 Consequences](../adr/ADR-0002-isolation-model.md) (FK cascades) | M | Deletion runs inside an explicit transaction with progress logging; soft-delete first (`tenant.status = 'deleted'`) so async purge can be scheduled off-peak (G8/G9 refine); quota system keeps per-tenant row counts bounded | G1 (schema), G9 (ops hardening) |
| R11 | **`X-Tenant-ID` header spoofing**: anonymous client sends the header to impersonate a tenant since it sits in the resolution chain | [ADR-0003 Decision 2.3](../adr/ADR-0003-routing-and-tenant-resolution.md) (guard rails normative) | H | Header honored **only** when the request carries a valid principal with membership in that tenant, or originates from the trusted internal allowlist; negative tests prove anonymous/spoofed headers are ignored; code review checklist item for G2 | G2 |
| R12 | **Refresh-token store compromise / replay**: theft of refresh rows or replay of a rotated token | [ADR-0004 Decision](../adr/ADR-0004-authentication-strategy.md) (rotating family) | M | Only hashes stored; rotation invalidates used tokens; reuse of a rotated token kills the whole family (theft detection); revocation lists are DB-backed so restarts preserve forced logouts | G2 |
| R13 | **Public-route enumeration**: unauthenticated endpoints (`/api/push/:pushToken`, badges by numeric id, `/api/status-page/:slug`) invite id-scanning across tenants | Survey [api-and-socket-events.md](./survey/api-and-socket-events.md) public routes; kept auth-free for ecosystem compatibility | M | Push tokens gain entropy requirements + rate limiting; badge/status visibility stays gated by data conditions which become tenant-scoped after G1 (wrong-tenant ids 404); slug space already user-chosen; systematic lock-down review scheduled in security phase | G6, G9 |
| R14 | **Socket room leakage across tenants**: stale rooms or mis-keyed emits deliver one tenant's beats to another client | [ADR-0004 Consequences](../adr/ADR-0004-authentication-strategy.md) (rooms rebuilt with `(tenant_id, user_id)` keys); plan G2 DoD | H | Room keys always `(tenantId, userId)` pairs derived from validated context (never raw client input); reconnect rebuilds rooms; forced logout leaves rooms; G2 integration tests assert cross-tenant emit isolation | G2 |

## Register hygiene

- Each risk names exactly one **Owning Phase** start point; phases listed together share delivery of the mitigation.
- New risks discovered during later phases append here with the next free ID and cite their source artifact — this file is the canonical register, per task G0.03.
- Risks R8/R9 were added during synthesis and trace directly to the ADR-0001 evidence trail; reviewers should confirm they agree the mitigations match the ADR text.
